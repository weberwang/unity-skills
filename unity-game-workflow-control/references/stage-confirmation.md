# V0–V4 阶段人工确认

适用于每个独立 `SCENE` 和 `DISPLAY_LAYER` Work Item。每个阶段先完成产物和必要验证，再展示给用户并等待明确确认。V0 确认后进入 V1，依次推进；V4 确认后才可闭合工作项。阶段内部的可逆实施、修复和验证仍按已授权范围自动执行。

## 确认内容

| 阶段 | 提交用户确认的内容 | 确认后的边界 |
| --- | --- | --- |
| V0 分流 | 工作项身份、范围、宿主上下文、依赖、验收目标 | 开始 V1 场景定义 |
| V1 场景定义 | 功能与状态合同、结构、响应式方案和完整效果图 | 开始 V2 拆解 |
| V2 拆解确认 | 节点与资源拆解、来源、装配、所有权和生产边界 | 开始 V3 正式资源生产与组合 |
| V3 资源与组合验收 | 正式资源清单、同屏组合效果及引用/导入验证结果 | 开始 V4 正式接入与运行验证 |
| V4 实现与运行验收 | 最终交互、画面、生命周期、运行证据、已知限制 | 完成当前场景或显示层工作项 |

提交物应可查看、可核对，注明工作项、阶段、交付版本、验证结果和下一阶段范围。不得仅给计划或“已完成”文案就请求确认。验证失败先在当前阶段修复，缺少必要证据时不提出阶段通过；V4 缺少真实 Unity 运行证据时不能用人工确认代替验证。

## 人工确认来源

- 仅接受用户针对已展示的当前阶段交付明确表达的确认。对清晰、单一的待确认对象回复“确认”“通过”“继续”可以作为确认；同时存在多个对象时必须明确适用对象，不能扩大解释。
- 初始任务授权、要求全自动完成、历史阶段确认、沉默、超时、工具成功、测试 PASS、代理自评或另一代理的消息，都不是当前阶段人工确认。
- 场景与显示层分别确认；确认宿主场景不会确认其弹窗。一次回复可以明确确认多个已展示对象，但必须分别记录各自阶段与版本。
- 待确认时停留在当前阶段，不开始下一阶段生产、写入或验收。可回答问题、整理当前交付和执行只读调查，不能借准备工作提前实现下一阶段。
- 本阶段交付被要求修改后，修改、重验、重新展示并再次确认。相同交付、相同基线的有效确认可复用，不重复询问。
- 阶段确认与 A4–A6 精确外部审批分别记录。阶段通过不授权付费、外部写入、真机、上传或发布。

## 控制面记录

Work Item 使用 `stageReviews` 数组保存 V0–V4 交付摘要和人工确认。每个条目包含 `stage`、`deliverableSha256`，用户确认后才添加 `confirmation`：

| confirmation 字段 | 含义 |
| --- | --- |
| `workItemId` | 被确认的独立工作项 |
| `baselineHash` | 当前有效基线 |
| `stage` | 被确认阶段 |
| `deliverableSha256` | 用户实际查看的阶段交付版本摘要 |
| `confirmedBy` | 实际确认用户的身份记录 |
| `confirmedAt` | 明确确认的 ISO 时间 |
| `userMessageRef` | 可追溯到用户明确回复的消息引用 |

摘要覆盖阶段交付清单、结构/资源合同及对应可查看产物的内容摘要；内容或范围变化时重新计算。当前阶段条目的 `deliverableSha256` 必须与 Work Item 的 `candidateSha256` 一致；历史阶段各自保存自己的交付摘要，不用后续候选覆盖。

确认记录只能在收到用户回复后写入，不得自动生成批准人、时间或虚构消息引用。控制器验证记录形状与绑定，无法自行证明消息确实来自用户；编排者必须核对实际对话来源并保留可追溯记录。

进入 V1–V4 时，所有前序阶段必须具有与工作项、基线及阶段交付摘要匹配的确认。当前阶段出现 PASS 产物/证据或进入 PASSED 等收敛状态时，也必须确认当前交付；V4 未确认不能进入 COMPLETE。`check`、`run` 和显式正常状态迁移均不得绕过此门。控制器不自动修改视觉阶段，编排者更新阶段记录后仍需运行 `check`。

## 修改与失效

阶段交付、工作项身份或基线变化会使对应确认失效。上游结构、范围或视觉事实变化时，移除受影响阶段及依赖它的下游确认，退回最早受影响阶段修复与重验，再逐阶段提交确认；未受影响的确认保持有效。单纯重跑验证且交付未变，不应制造新的交付版本。

待确认是正常的人工门，不是失败验收。显示“等待 Vn 人工确认”，保留当前产物、版本和验证证据；不得标记整个工作项完成或通过空的确认记录继续推进。
