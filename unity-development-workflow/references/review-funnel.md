# 多级漏斗审核

## 何时读取

任何候选集需要视觉、技术、质量或发布审查时读取。该机制用于减少重复审查和用户中断，但不降低最终门禁强度。

## 输入

- 当前对象、版本、来源修订及全部候选的 ID、路径和 SHA-256。
- 验收标准、风险策略、硬性约束与上游批准证据。
- 各级原始检查结果、专业审查记录和用户批准原件。

## 执行步骤

所有候选严格按 F0-F3 顺序收敛；下一级输入必须精确等于上一级输出，候选数量只能减少，不能在中途新增、替换或回填：

1. **F0 自动预检**：对全部候选执行 Schema、证据哈希、版本链、硬性策略、尺寸/格式和可重复检查。失败候选立即移出，不消耗人工审查。
2. **F1 主责筛选**：主责人基于验收标准、差异和已知风险把合格候选压缩到最多三个。该级是筛选记录，不是批准；产出者可以说明取舍，但无权批准自己的输出。
3. **F2 专业审查**：独立审查者只审查 F1 短名单，按对象类型执行所需学科并合并阻塞项、重要修改和建议。视觉对象必须由视觉一致性、Unity 可实现性、UX/可读性三个不同任务和不同审查者完成，并收敛到唯一推荐候选。
4. **F3 用户裁决**：只向用户提交唯一推荐候选、合并结论、未消除风险及有实质取舍时的一份备选说明。用户批准必须绑定该唯一候选的 ID、版本、SHA-256、来源修订与 F0-F2 证据；F3 不重新扩展候选集。

每一级记录 `inputCandidateIds`、`outputCandidateIds`、状态、决定摘要和证据。状态只允许 `PENDING`、`PASS`、`CHANGES_REQUIRED`、`REJECTED`、`BLOCKED`。任一级未通过后，下游全部保持 `PENDING`。

## 风险策略

- `STANDARD`：普通场景效果图、单项资源和局部实现；完整执行 F0-F3。
- `ELEVATED`：共享资产、跨场景 UI、性能敏感或返工代价高的对象；F1 必须显式列出跨模块影响，F2 必须覆盖全部受影响学科。
- `CRITICAL`：Visual Bible、架构边界、隐私/商业能力、候选制品和发布；除完整漏斗外，还必须执行对应质量门与发布授权，漏斗不能代替专项门禁。

风险策略只能增加检查和证据，不能跳过级别。低风险快速通道若无需外部批准，可直接实现与验证；一旦进入审核，仍使用完整 F0-F3。

## 修改与回退

- F0 或 F1 发现候选本身无效：回到候选生产阶段，创建新版本后从 F0 重启。
- F2 仅发现表达、证据或可局部修复问题：根据影响返回 F1 或 F2；候选像素、结构、行为、规格或版本变化时必须返回 F0。
- F3 请求修改：返回最早受影响级；任何候选内容变化都必须从 F0 重跑，不得只补签 F3。
- 被淘汰和旧版本候选保留为历史证据，但不得重新进入当前漏斗。需要恢复时必须作为新版本重新进入 F0。

## 子代理角色与并行边界

- F0 检查可按候选并行；F1 由一个主责人统一筛选，避免多个筛选者产生不一致短名单。
- F2 各专业审查可并行，但必须使用不同任务和不同审查者；主代理只能合并结论，不能修改独立原始意见。
- F3 是单一外部用户门禁；代理不得代批，也不得并行提交不同候选诱导多次批准。

## 所需锁与 Unity 权限

- 纯证据检查和只读审查不需要 Unity 写权限；候选修订必须重新取得对应资源写锁。
- 审核期间冻结候选内容和路径；任何写入都会使当前级及下游证据失效。
- F3 用户批准原件按严格执行策略处理，代理无权创建、改写或补签。

## 机器可读输出

视觉审核写入 `visual-review.yaml` 2.0：`candidateEvidence` 为入口候选全集，`funnel.stages` 固定为 F0-F3，`selectedCandidate` 必须等于 F3 唯一输出。`APPROVED` 仅在四级全部 `PASS`、F2 独立审查齐全、当前候选完成阶段拷问且 F3 用户批准有效时成立。

## 通过条件

- F0 输入覆盖全部入口候选；每一级输入等于上一级输出，输出是输入子集。
- F1 最多保留三个候选；F2 和 F3 通过时均只保留同一个候选。
- 每个通过级都有原始证据；最终候选与审查主体版本一致。
- 产出者没有创建独立审查批准；用户只在 F3 对已收敛候选作决定。

## 失败与恢复出口

出现跳级、候选扩容、级间 ID 不一致、通过但无证据、F2 多候选、F3 换候选、审查者复用或批准版本不匹配时标记 `BLOCKED`。不得用口头说明补齐机器记录。
