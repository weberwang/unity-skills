# 文本与色彩拆分路线

在 V2 拆解冻结效果图、选择视觉来源时使用；V3 资源生产和组合、V4 接入沿用同一拆解结果。本文只补充路线判断，使用既有 `visualRouteAnalysis`、`assemblyAnalysis`、`layoutBinding` 和资源记录，不新增 schema、阶段或审批。

## 完整拆解与视觉显著性

在不影响功能和既定视觉目标的前提下，完整识别位图中的可独立部件，包括文字、图标、底板、色彩填充、边框、光影和装饰。每项保留稳定编号、来源、实现路线和消费节点，系统文本及原生填充也必须进入拆解与图内标注，不能因无需生成图片就遗漏。完整指职责与覆盖完整，不按每个字、每种颜色或每个装饰细节机械切碎；拆解是识别与独立生产，不能裁切或抠取参考图充当正式资源。

先判断视觉作用、特征显著性、内容变化与复用需求，再核对项目实际渲染能力。明显承担主题、情绪或识别作用的特殊字形、材质、纹理、轮廓和光影优先保留独立资产；视觉特征不明显的操作文字优先考虑系统文本，简单填充和规则边框优先考虑原生绘制。不能仅凭元素名称、静态/动态属性或“程序可以画出来”决定路线。

拆开视觉来源不拆散功能归属。按钮、进度条等仍由原组件统一管理点击热区、输入、状态、动态更新、本地化、显隐和生命周期；装配按[节点树与组件分组](ui-layout-and-hierarchy.md#细组件分组)记录真实依赖。位图与原生节点可以属于同一功能组件，但分别登记来源，不能用单一区域 `COMPOSITE` 隐藏混合来源，也不能把完整组件或整屏烘焙成不可交互的图片。

默认 `usability` 下，低显著性文字的替代字体、简单填充的轻微装饰差异可在 V2 说明，但不能改变文案、语义、可读性、视觉层级或状态识别。明显美术特征及明确要求保留的效果仍须保留；`exact` 或指定字体、效果时遵守对应精确要求。路线和替代依据写入既有分析与 brief，随编号拆解图一并人工确认，不额外增加文字方案确认；实际显示效果仍由用户检查，技术检查不代替视觉验收。

## 文字路线判定

系统文本指项目实际使用的 uGUI/TextMeshPro 文本组件或 UI Toolkit `Label`/`TextElement`，沿用项目字体、本地化与数据绑定，普通文案无需逐段生产字图。字体、图集和材料采用项目已有能力，不能默认两种 UI 系统支持相同的字形效果。

| 文字特点 | 拆分与实现 |
| --- | --- |
| 视觉特征不明显的操作标签、正文、提示或数值 | 优先系统文本；登记字体来源、字重、字号、字距、行距、基线、对齐、换行、所需效果与内容来源，保持独立文本节点。 |
| 特殊字形、金属质感、裂纹、立体光影或跨字装饰共同构成的固定美术字标 | 优先整段独立字图，保留整体构图与跨字效果；与底板、徽章可可靠分离时分别登记，不机械逐字切分。文案语义仍由功能组件保存。 |
| 需要更换文案、本地化或多处复用的统一字形风格 | 优先复用覆盖所需字符的字体资产及配套材质，必要时评估位图字形或文字与独立效果分层方案；按实际来源登记字形、材质与图片依赖，程序负责更新和排版。 |

选择系统文本后，当前字体和 renderer 必须实现方案要求保留的字形、填色/渐变、描边、阴影、发光与排版，并提供实际方法及可核验依据。能显示同样文案、同名字体或存在文字组件，都不足以证明效果还原。不得在实现时静默删去已确认效果、猜用默认字体或提高容差使路线通过；能力不足时修订受影响方案。

动态数值、本地化和状态变化文字不能烘焙为固定字图。复用字形或分层方案也须满足字符覆盖、字距、换行和效果；整体效果无法可靠分离时，固定文字保留完整原子字标，可变内容则报告能力缺口并调整方案，不能以固定结果代替动态内容。字体资产、贴图和材质外观按真实来源登记，文字组件加载和排列这些资产不使其变成纯程序绘制。

例如战斗失败弹窗：「战斗失败」的金属立体字、裂纹和跨字火光可作为整段独立字图；带统一字形风格的提示按文案变化与字符覆盖选择字图或字体资产；普通「返回」操作标签使用系统文本，按钮发光底板独立生产。三者分别编号，按钮文字与底板仍由同一功能组件管理输入及状态。

字体、多语言与响应式接入遵守[文本与响应式合同](visual-workflow.md#文本与响应式合同)及[TMP 字体图集流程](tmp-font-atlas-workflow.md)。参考图物理像素不能直接当作 TMP 字号或 UI Toolkit 逻辑尺寸；结合 CanvasScaler、PanelSettings、实际字形度量与容器验证，保留字体来源事实，不把替代字体冒充原字体。

## 色彩填充路线判定

填充与文字使用同一判断顺序。颜色本身、静态/动态属性、程序能否绘制渐变不能单独决定路线；先判断颜色与材质、光影是否共同承担主要视觉价值，再选择独立位图、复用表面或原生绘制。

| 填充特点 | 拆分与实现 |
| --- | --- |
| 明显金属、玻璃、纹理、立体光影、复杂辉光或不规则色面 | 将材质表面独立生产为位图；与边框、装饰可可靠分离时分别登记，否则保留完整原子部件。 |
| 有统一风格、需多处复用的渐变或纹理表面 | 优先复用已确认的填充贴图，按实际需要使用九宫格、遮罩或分层装配；只有项目现有原生能力能保留所需风格时才选择原生路线。 |
| 视觉特征不明显的纯色、透明色、简单规则渐变或规则边框 | 优先原生绘制；登记形状边界、颜色、透明度、边框、圆角、渐变和适用状态，证明当前 UI 系统的实际实现能力，不能假定简单渐变或圆角天然受支持。 |

例如返回按钮的蓝色表面若含明显高光、辉光与纹饰，应保留对应位图；只有可分离且视觉特征不明显的基础蓝色填充才交给原生绘制，金属边框和装饰继续独立登记。弹窗简单半透明黑色遮罩可用原生填充，带裂纹和材质的深色面板保留位图，不能因同为色面就统一替换成纯色矩形。

拆开的填充、边框和装饰共用原组件的形状边界、圆角、裁切、布局与状态来源，避免接缝、重复叠色或透明度叠加。进度比例、选中/禁用颜色保持运行时可变；位图负责风格表面，程序负责实际比例或状态。填充与光影无法可靠分离，或拆分会损伤功能和既定外观时，保留完整部件并记录原因，不为减少位图强行拆分。

## 合同记录与交接检查

- 字体、字形/效果贴图、材质、填充表面与九宫格按[公共资源登记与使用](shared-asset-usage.md)先查库再选择复用或生产；多个本地拆解编号可以绑定同一公共资源身份，资源交接同步总表与消费关系。纯原生样式参数引用已有规范和实现，不虚构资产文件或 GUID。
- `visualRouteAnalysis.distinctiveVisual` 记录实际观察到的特征与显著性，`routeReason` 说明视觉作用、变化/复用需求及替代依据；明显美术特征遵守现有资产优先规则，不伪报 `isDistinctive=false` 获取原生资格。
- `UNITY_NATIVE` 在 `nativeSuitability` 记录实际原语、理由与证据，使用既有 `TEXT`、`BASIC_GEOMETRY`、`PROGRESS` 或适用原语；具体字体/填充参数放入既有 brief、规格与验证材料，不向受 schema 约束的对象添加未定义字段。不能完整表达所需外观与状态时，采用独立资产或修订方案。
- `assemblyAnalysis`、`semanticGrouping` 与 `layoutBinding` 绑定每项消费节点、真实父级及功能组件。V3 同屏组合核对文字/表面依赖、裁切、状态同步、命中和无遗漏；V4 验证真实数据、本地化、比例与输入，截图及显示效果由用户人工确认。

上述检查沿用现有 V2/V3/V4 交付与确认。图片生成、字体授权、付费、外部写入及运行验证继续遵守各自既有边界；本文不授权自动分析截图、启动 Player 或真机。
