# SDK 统一初始化

项目实际采用的 SDK 统一由 TDD 映射的唯一初始化入口负责。默认入口为 `Assets/Scripts/Foundation/InitializeSdks.cs`，由启动 Composition Root 在首个场景开始前调用一次；若项目既有结构使用其他路径，只在 TDD 固定该唯一映射。没有采用 SDK 时不创建占位文件，也不因本规范增加 SDK、UPM 包或平台依赖。

## 唯一入口与职责

- 入口只投递各 SDK 自己的初始化任务并立即返回，不等待整批结果。首帧、Boot 场景和首个游戏场景不得等待任何 SDK 批次完成。
- 所有已采用 SDK 的配置校验、平台分流、初始化调用、真实完成回调处理、幂等状态、操作身份、失败分类和初始化重试集中在唯一入口。可使用按 SDK 分开的私有方法和状态，但不得把实际初始化、第二份状态或恢复计时器散落到广告服务、隐私模块、Scene、MonoBehaviour 构造或平台启动入口。
- 公共类型、纯配置、原生插件安装与必要宿主设置留在其职责文件。平台适配器可以封装原生 API，但不能在模块导入、对象构造或场景生命周期内自行启动 SDK。
- 广告加载/展示、支付交易、登录界面、埋点业务和隐私交互继续归各自业务模块。SDK 就绪后的广告位加载恢复等运行任务由所属服务持有；业务模块通过已注入接口读取 SDK 状态或请求单个 SDK 重试，不直接依赖第三方 SDK API。
- SDK 导入不能产生模块级初始化副作用。可选 SDK 的动态加载或调用错误在各自任务内部捕获，避免影响共享入口和其他任务。

## 独立启动与官方前置

1. 对每个已启用且当前平台支持的 SDK 分别投递任务。某 SDK 配置错误、同步抛错、异步失败、重试或永不回调，都不能阻止其他任务开始。
2. 不建立跨 SDK 顺序链、依赖启动图或 `allSdksReady` 屏障；禁止“等待 SDK A 完成再启动 SDK B”，也禁止等待全部 SDK 完成才进入首帧或首个场景。所有任务投递后可另行汇总诊断，但汇总不属于游戏启动前置。
3. 每个 SDK 只等待自己的平台、配置、宿主或桥接条件。未满足时将该 SDK 标记为待初始化/受限，不让其他 SDK 或首帧陪同等待。
4. 不得绕过锁定版本官方明确要求的真实前置。如果前置导致一个 SDK 当前无法独立初始化，记录 SDK、锁定版本、前置条件和来源，只限制该 SDK；继续启动其他无关 SDK，不伪造成功，也不以“核心 SDK”建立全局启动门。
5. 初始化解耦不授权提前执行广告、支付、跟踪等业务动作。业务服务仍检查 SDK 就绪状态、真实隐私状态和自身操作条件。

## 幂等、回调与隔离

- 同一应用生命周期和同一有效配置下，每个 SDK 只初始化一次；重复调用复用该 SDK 的进行中或已完成状态，不重启其他 SDK。配置被替换、SDK 被禁用或所属生命周期销毁时，只使该 SDK 的旧操作失效。
- 只有该 SDK 真实完成回调或锁定版本官方明确的就绪信号才能记为成功；初始化函数返回或请求已受理不代表完成。超时本身不能伪造成功或失败。
- 每个 SDK 独立记录操作 ID、错误分类、失败次数、截止时间和最多一个初始化恢复任务。迟到或重复回调不得覆盖新配置或更新的操作状态。
- 可恢复的初始化失败只按该 SDK 的合同重试，手动重试只重新尝试目标 SDK。配置错误、平台不支持或官方前置未满足时保持明确受限，直到相应条件变化，不盲目循环。
- SDK 初始化恢复与广告位加载、支付交易和其他业务恢复分开管理，不共享重试计数、计时器或取消状态。
- 诊断只记录 SDK 身份、平台、阶段和脱敏错误类别，不记录 SDK Key、凭据、设备标识或完整原生异常。

## TDD 与验收记录

在 TDD 和实施包中记录实际 SDK、锁定版本、目标平台、配置来源、各自官方前置、真实完成信号、状态所有者、失败分类、初始化恢复所有者和业务使用边界。真实 Android/iOS 系统回调只按目标平台的授权验证计划核对；本规范不授权自动启动真机，也不替代第三方 SDK 的实际安装、控制台配置或集成验证。

针对 Unity 工程的定向验证应覆盖：多个 SDK 各自发起；单一 SDK 抛错、拒绝、失败或不回调时其他 SDK 与首帧不受阻；重复入口、配置切换和迟到回调；平台不支持与 SDK 自身官方前置；单 SDK 重试不重跑其他 SDK；业务期重试与初始化恢复相互隔离。
