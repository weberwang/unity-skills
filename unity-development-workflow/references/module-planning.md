# 模块规划

## 何时读取

全局技术设计阶段、S00 前，以及共享职责或依赖关系发生变化时读取。

## 输入

- 已通过的项目发现结果、用户需求与场景清单。
- 已批准的技术边界和现有程序集定义。
- 各场景实际需要复用的能力。

## 执行步骤

1. 将代码与资源职责划分为 Foundation、Shared、Gameplay、Presentation、Content、QA、Delivery；将制作、架构、玩法、数值、视觉资源、音频、QA 性能和发布角色映射到所属模块与交付物。
2. 为每个模块指定路径所有权、负责人、公共接口和依赖。
3. 生成 `module-manifest` 与有向无环图 DAG。
4. 检查循环依赖、重复所有权和未声明跨模块访问。
5. 禁止运行时代码引用跨模块 Editor 实现；Editor 依赖只能留在对应 Editor 边界。
6. 仅当至少两个场景共同需要某能力时，才将它上移到 Shared 或 Foundation。
7. 对外只暴露当前需求所需的最小公共接口；存档、输入、时间、随机、场景加载、平台和第三方服务都通过明确边界接入。
8. 为每个实现增量定义玩家行为、代码入口、资源依赖、测试入口、性能预算和下游交接，不以“完成模块文档”代替可运行实现。

## 子代理角色与并行边界

- 各模块规划代理可并行提出边界和接口草案。
- DAG 合并与冲突消解由一个架构审查代理串行完成。
- 模块所有者只能修改自己路径；公共接口变更必须重新审查下游。

## 所需锁与 Unity 权限

- 规划阶段只需只读权限。
- 写入 manifest 需制品路径锁；若落地 asmdef 或目录则需 Unity 项目写锁并显式绑定实例。

## 机器可读输出

输出 `module-manifest.yaml` 与 `module-dag.json`，记录模块、路径、代码/资源/文档所有者、公共接口、依赖边、实现增量和审查结论。

## 通过条件

- 七类模块职责明确且路径所有权不重叠。
- DAG 无环，所有跨模块依赖均已声明。
- 不存在跨模块 Editor 实现引用；共享上移满足“两场景共同需要”。

## 失败与恢复出口

- 出现依赖环时拆分接口或重新归属，不得用忽略规则放行。
- 所有权冲突时暂停相关写入，由主代理重新分配路径。
- 公共接口无法收敛时保持规划阶段并请求用户裁决需求边界。
