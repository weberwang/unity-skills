# 工作流总览

## 何时读取

每次启动、恢复或重新规划 Unity 工作流时首先读取；把它作为其余参考文件的阶段导航。

## 输入

- 用户目标、目标场景和交付边界。
- 当前项目路径、已有机器可读产物与证据目录。
- 用户已经明确批准或拒绝的视觉版本。

## 执行步骤

1. 先按影响选择快速、标准或发布通道；标准/发布按“G0 立项 → 项目发现 → 全局技术/视觉设计 → S00 → G1 垂直切片 → G2 场景小循环 → 全局回归 → G3 Windows 交付”推进。
2. 先执行只读项目发现；失败时进入恢复出口，不得写入。
3. 形成全局技术方案与 Visual Bible，取得用户视觉批准。
4. 完成 S00 共享骨架和空壳构建，选择一个代表性场景完成 G1 垂直切片，再逐场景执行 G2 小循环。
5. 每个阶段建立“输入 → 执行者 → 原始结果 → 独立审查 → 用户决定”的证据链。
6. 每个场景在内部重复“实现 → 游戏效果图/资源 → UI 效果图/实现 → 实机对比 → 独立审查 → 用户确认”，直到冻结；全部冻结后执行全局回归和 G3 Windows 交付。

快速通道对已批准的局部低风险任务直接实现和验证，不强制维护控制面或 G0 至 G3。主代理只编排任务、维护状态、合并审查意见和请求批准；实际发现、实现、测试、视觉生成、审查与交付检查尽量由子代理承担。

## 子代理角色与并行边界

- 并行执行互不写入同一 Unity 项目的只读调查、设计候选、测试分析和报告整理。
- 串行执行同一项目的正式写入、共享状态变更和主场景验收。
- 开发代理与审查代理必须独立；开发代理不能自批。
- 任一时刻只允许一个主场景处于验收阶段。

## 所需锁与 Unity 权限

- 项目发现阶段只需只读权限。
- 任何 Unity 写调用前都必须发现并显式绑定唯一 `unity-mcp` 实例。
- 正式写入需获得目标资源的独占锁；共享状态需获得全局独占锁。

## 机器可读输出

输出 `workflow-state.json`，至少包含 `channel`、`gate`、`phase`、`active_scene`、`approvals`、`evidence`、`blocked_reason` 和 `next_gate`。

## 通过条件

- 当前阶段的前置门禁有可追溯证据。
- 当前通道与任务影响匹配，未维护无关角色和交付物。
- 独立审查与用户批准状态明确，且代理未代替用户批准。
- 下一阶段所需参考文件、权限与锁均已确定。

## 失败与恢复出口

- 缺少证据、实例、锁或批准时标记 `BLOCKED`，保持在当前阶段。
- 修复只读发现问题后从项目发现重跑；视觉被拒绝时返回对应视觉循环。
- 场景失败只回退该场景；共享骨架变化则重新评估所有下游场景。
