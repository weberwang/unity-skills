# 视觉工作流

## 何时读取

定义全局视觉方向，生成或编辑游戏/UI 候选，处理透明素材，或进行效果图与实机审批时读取。

## 输入

- 用户视觉目标、平台限制、内容边界与已有品牌资产。
- Codex ImageGen 可用能力、候选图片、场景 manifest 和 UI 信息架构。
- 已批准版本、审查意见与实机截图。

## 执行步骤

1. 以 `image-generation` 契约创建出图任务，生成多张相互独立的全局视觉方向图，再制作仅用于比较的联系表。
2. 记录色彩、材质、光照、构图、镜头、字体、图标、UI 密度和禁用项，形成 Visual Bible。
3. 由视觉一致性、游戏可实现性、UX/可读性三个审查代理分别评估。
4. 主代理合并为一份无冲突、可执行且标明优先级的修改清单；按清单生成新修订并重新审查，直到请求用户最终批准。
5. 每个场景分别执行游戏效果图和 UI 效果图循环；每轮记录接受、拒绝和已解决意见，候选版本不可覆盖已批准原图。
6. 使用 Codex ImageGen 生成或编辑位图；保留提示词、输入版本、输出版本与用途。
7. 简单纯色背景可做透明色键处理；复杂边缘、半透明、毛发或混合背景必须阻塞并请求合适源素材，不得伪造透明结果。
8. UI 效果图只定义视觉目标；必须用 UI Toolkit 实现可交互 UI。
9. 先读取 `mcpforunity://scene/cameras` 核对固定机位，用官方 `manage_build` 构建，再运行 `scripts/capture_windows_runtime.py` 启动 EXE、捕获实际窗口并生成 `CAPTURED` 实机证据；按同一三代理审查、修改、重构建、重新捕获和用户批准门禁对比效果图。
10. 需要把效果图变成运行时素材时进入资源流水线；联系表、效果图和未审拆分图不得直接导入正式场景。

## 子代理角色与并行边界

- 候选生成可并行，但每个候选必须是独立图片；联系表不能作为生产源图。
- 三个审查代理独立输出，不能互相覆盖结论；主代理只合并修改清单。
- 视觉生成与 Unity 写入可并行准备，批准前不得将候选写成正式视觉状态。

## 所需锁与 Unity 权限

- 图片生成只锁定各自输出路径，不需要 Unity 写权限。
- 导入已批准素材或捕获实机效果前，显式绑定 `unity-mcp` 实例并取得目标资源锁。
- 用户视觉批准是外部门禁，任何代理均无权代替。

## 机器可读输出

输出 `visual-bible.yaml`、`image-generation.yaml`、逐候选 `image-task.yaml`、Editor 固定机位 `visual-capture.yaml`、Windows 构建实机 `runtime-visual-evidence.yaml` 和逐轮 `visual-review.yaml`。最终审查记录轮次、候选证据、三份不同子代理审查、合并修改清单和用户决定；`image-task` APPROVED 必须引用与候选视觉版本一致的最终 APPROVED 审查。实机证据绑定场景、构建版本、源码修订、构建制品哈希、截图哈希与尺寸。

## 通过条件

- Visual Bible 与当前场景候选均具备版本化证据。
- 游戏效果图、UI 效果图和实机效果完成三代理审查及用户视觉批准。
- 复杂透明素材未被自动降级，UI 最终由 UI Toolkit 实现。

## 失败与恢复出口

- 用户拒绝时保留版本与原因，按单一修改清单生成新候选。
- 三方意见冲突时主代理先消歧；无法消歧则向用户展示明确取舍。
- 复杂透明处理阻塞时请求分层源文件、遮罩或干净背景素材。
