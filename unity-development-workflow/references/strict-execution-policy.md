# 严格执行策略

## 何时读取

每次启动、恢复、推进状态、请求批准、调用 Unity MCP 写入或判断场景完成时读取。适用于快速、标准和发布通道，优先于进度、成本与并行效率。

## 输入

- 当前通道、状态、场景、任务 DAG、适用门禁与版本链。
- 用户确认、独立审查、原始检查结果及其 ID、版本、SHA-256、`sourceRevision` 和范围。
- Unity 实例、Editor 状态、目标基线、路径所有权与锁。

## 执行步骤

1. **默认拒绝**：缺少明确允许条件、版本化通道决策、权限、锁、批准或证据时一律不允许推进。未判定生命周期门默认适用；进入 G0-G3 后必须执行该门完整标准 `requiredChecks`，不得以不适用、删减、增补或错配检查绕过。
2. **失败即阻塞**：必需检查为 `FAIL`、`BLOCKED`、`NOT_RUN`、结果未知或工具异常时，保持当前状态或标记 `BLOCKED`。
3. **不得跳关**：先以版本化通道决策列出适用生命周期门，再按依赖顺序执行。快速通道不产生 G0-G3 通过状态；一旦任务需要 Unity/MCP 写入、正式资源、场景/Prefab、共享登记或批准状态变更，必须升级到标准或发布通道并执行完整门禁。
4. **设备验证仅在研发完成且用户明确要求后执行**：任何安装后 Standalone/Player 运行、真机或等价设备采样、设备档位测试、安装升级、设备输入、生命周期、视觉、性能或稳定性验证都属于设备验证。G2 必须先完成全部批准模块、场景、Editor 验证和无设备平台适配；G2 `PASS` 后 G3 才可生成候选主制品，但仍严禁自动发起真机或等价设备验收。研发阶段只允许 Editor/EditMode/PlayMode、Game View 模拟、静态预算和构建产物生成。
5. **确认绑定版本**：所有用户确认和代理审查记录执行者、时间、对象 ID、版本、SHA-256、`sourceRevision`、上游证据和结论范围。口头认可、模糊的“继续”、旧版本确认或无对象确认不构成通过。
6. **代理不得代批**：代理可以审查、推荐和汇总，不能代替用户完成范围、拆分、A0 全局三选一、A1 草图/结构、A2 高保真精确版本、A3 资产地图、风险接受或发布放行。开发代理不得批准自己的输出。
   本地 approval 文件与 SHA-256 只能证明内容未变，不能单独证明批准者身份。代理禁止创建、改写或补签用户批准原件；必须引用宿主对话中的真实用户事件或宿主提供的只读/签名批准收据。当前宿主无法提供可验证批准事件时，机器门禁只能标记“内容绑定已验证、用户身份未验证”，涉及外部供应商调用、付费、签名、上传、发布或覆盖稳定制品的动作必须保持 `BLOCKED`。
7. **上游变化递归失效**：上游内容、版本、哈希、来源修订或批准范围变化后，立即使全部依赖状态和证据失效并回到最早受影响门禁；旧结果只保留为历史。
8. **无证据不通过**：`PASS`、`APPROVED`、`VERIFIED`、`DONE` 只能来自当前版本的可读取原始证据。摘要、计划、代理声明、Git 提交或文件存在本身不能替代实际结果。
9. **场景小循环不可跨越**：单个场景的 A1 草图确认、A2 高保真确认、A3 资产地图确认与逐项生产、A4 结构化还原和清理验证闭环后才能冻结并切换下一主场景。下一场景只能只读准备；任何设备验证均不属于单场景小循环，并由 G3 独占且等待用户明确要求。
10. 每次 Unity MCP 写入前：发现实例，按规范化项目路径选择唯一实例并显式绑定；读取 Editor 状态；校验当前门禁、上游版本/批准、目标基线和独占锁；读取目标对象并保存写前证据。零个或多个实例匹配、Editor 忙碌、场景未保存、连接陈旧、状态或基线不符时禁止写入。
11. 每次 Unity MCP 写入后：等待导入、编译和域重载结束；再次读取 Editor、目标对象、场景、Console 与登记；核对 GUID/稳定 ID、序列化引用和实际差异；运行最小验证并保存原始输出与 SHA-256。后置校验失败时停止后续写入，不得以 MCP 调用成功推进状态。

## 子代理角色与并行边界

- 子代理只在已批准范围、有效前置和明确所有权内工作；任何代理发现失效、未知或失败都必须上报并停止受影响推进。
- 开发与审查角色分离；审查代理无权代替用户门禁。
- 不同场景可并行只读准备；当前主场景闭环前，其他场景不得正式写入或验收。
- 同一 Unity 项目的正式写入和共享状态迁移串行，同一路径、资源、Prefab、场景或 DCC 源只有一个写入者。

## 所需锁与 Unity 权限

- Unity MCP 写入必须绑定唯一实例，并由 Codex 明确分配目标路径、资源、场景和共享状态的单写者。
- Editor 未稳定、实例不唯一、所有权重叠、目标基线不符或上游批准失效时禁止写入。
- 只读任务不得借权限升级修改项目；写入后必须完成后置校验再释放锁和转移所有权。

## 机器可读输出

记录适用门禁、当前状态、对象 ID/版本/SHA-256、`sourceRevision`、上游证据、用户确认、独立审查、失效关系、Unity 实例、写前/写后快照、锁、命令、原始结果、阻塞原因和下一门禁。每次状态迁移记录执行者与时间。

## 通过条件

- 前置状态、依赖、锁、权限和唯一 Unity 实例全部有效。
- 用户门禁和独立审查均绑定当前精确版本，角色符合要求。
- 所有必需证据可读取、哈希一致、来源可信且结果为实际通过。
- 没有未处理失败、失效证据、未知项、跳关或跨场景写入。
- Unity MCP 写前与写后校验均有当前证据；场景小循环已经完整闭环。

## 失败与恢复出口

- 任一条件无法证明时结论必须为“不推进”，禁止以进度压力、人工目测、代理共识或“稍后补证据”放宽。
- 修复失败后，从失败检查及全部受影响下游重新执行，不直接恢复旧通过状态。
- 用户批准对象变化时生成新版本并重新请求批准，不覆盖原记录。
- Unity MCP 状态不确定时停止写入，重新发现实例并从写前校验开始。
- 当前场景无法闭环时保持其为主场景；只有用户明确取消或缩减当前版本范围并形成版本化决策，才能结束该循环。
