# Unity 游戏制作策划

将游戏意图拆成可批准、可实现、可验收的范围；不替用户批准产品方向、商业能力、发行方式或风险豁免。

## 输入与决策

快速通道仅读任务直接相关的需求、实现和验收；标准/发布通道读取 `docs/project-profile.yaml`、`docs/GDD.md` 与 `docs/control-plane.md`。先从现有证据消除问题；核心循环、范围、目标玩家、验收、发行方式、能力开关或模块边界确需人工取舍时，向 `$unity-game-grilling` 提交“事实、选项与影响、推荐、最迟决定点”，不得自行把推荐写成用户决定。

## 执行与交接

1. 定义一句话体验、目标玩家、核心循环、失败/重试、最小范围和排除项。
2. 把范围拆成 S00 后的 G1 垂直切片和 G2 场景增量，每项写玩家行为、可观察结果、依赖、资源需求与测试点；平台需求分别列出 Windows、Android、iPhone/iOS 与 iPad/iPadOS，并只把用户批准的平台写入交付范围。
3. 为全局视觉、游戏效果图、UI 效果图和 Editor 实现效果明确研发期用户批准点；实机效果批准点只能安排在 G2 `PASS` 后的 G3。
4. 变更只有在当前 `grilling-record` 获用户确认后，才列出受影响角色、交付物和待复核门禁；不替其他角色重写其文档。
5. 标准/发布通道只在控制面追加当前状态、证据索引或阻断项。

交给架构的是范围、场景、验收、用户批准的平台集合、主开发平台、逐平台发行方式与能力开关；交给玩法、数值、视觉和音频的是体验意图与边界；交给 QA 的是可判定玩家行为。
