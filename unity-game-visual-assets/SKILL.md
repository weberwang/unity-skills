# Unity 视觉与资源接入

视觉流程必须按“全局视觉 → 低保真 Prefab/Scene 结构说明 → 用户确认 → 高保真效果图 → 用户确认送审候选 → 三类独立审阅 → 效果图完整编号框选/分类 → 用户确认资产地图 → 逐项独立生成/审查 → 正式结构化 Prefab/Scene/UXML/USS 拼装 → 清理运行时灰盒与占位 → Unity 验证”推进。任一确认缺失或上游版本变化时，下游任务保持阻塞。生产级 3D 模型与 PBR 贴图分别交给 `$unity-game-3d-modeling` 和 `$unity-game-3d-texturing`，本角色只提供艺术方向、参考边界和最终视觉一致性审查。

## 输入与决策

读取 Visual Bible、当前场景 manifest、UI 信息架构、资源依赖、资源登记和性能预算。视觉方向、生成式资源、授权、预算、透明处理或发布资格需要取舍时，先交给 `$unity-game-grilling` 逐项确认并生成绑定当前候选的批准记录，再向总控提交决策包。Visual Bible、P0 低保真结构、P1 高保真送审、P3 资产地图和最终实机视觉批准均是强制触发点；缺少当前版本记录时不得进入下一阶段或写入受影响正式资产。

## 执行与交接

1. 建立全局设计支柱、世界与 UI 语言、色彩、材质、光照、镜头、字体、图标、动效、可读性和禁用项；生成相互独立的方向图，完成视觉一致性、Unity 可实现性、UX/可读性审查，合并意见并请求用户批准 Visual Bible。全局视觉未批准时不得进入场景结构设计。
2. 每个场景先提交低保真 Prefab/Scene 结构说明，包括灰盒图、层级树、稳定节点 ID、父子关系、渲染顺序、图片/文字/图元/3D/VFX 分类、交互与状态、Anchor、Pivot、安全区、遮罩和资源占位 ID。UI Toolkit 场景同时说明 UXML/USS 与 UIDocument 结构。用户未确认当前结构版本时，不得生成高保真效果图。
3. 依据已批准 Visual Bible 和低保真结构分别生成游戏内与 UI 高保真效果图，版本化提示词、输入和输出。效果图不得暗改结构；需要新增、删除、合并节点或改变交互时，先回退并重新确认低保真结构。用户确认高保真图仅表示它可以成为送审候选，不代表其中任何像素已获准作为运行时资源。
4. 将送审候选分别交给视觉一致性、Unity 可实现性、UX/可读性三类独立审阅，开发者不得审查自己的输出。任何修改都会产生新的高保真版本，并必须重新取得用户的送审确认和三类审阅；三类审阅均通过后，才可在该同版本效果图上用稳定编号框选全部待生产单图，同时把每个可见元素分类为“独立生成图片、已批准资源复用、文本、Unity 图元/程序绘制、UXML/USS/矢量、材质/VFX、3D 对象”之一；不得存在未框选、未分类或无法映射到结构节点的可见元素。
5. 把编号标注图、分类表、结构节点映射、用途、状态变体、目标尺寸、透明度、Pivot、Anchor、PPU、九宫格和排序信息组成资产地图，请求用户再次确认。资产地图未确认时不得启动单图生产；上游结构或高保真图变化时，使资产地图及受影响下游批准失效。
6. 按资产地图编号逐项创建独立生成或重绘任务，以已批准 Visual Bible 为唯一风格权威，并逐项完成视觉、技术和 UX 审查。截图和高保真效果图只允许参考内容、构图或信息层级；禁止复制其成品像素，禁止裁切截图或效果图作为 Sprite、纹理、UI 图或边带背景，也禁止把裁片轻微修饰后冒充独立生成资源。只有已批准的原始独立资源或具有可验证独立图层身份的源文件才可复用或导出。
7. 全部单图批准后，严格按已确认结构版本拼装正式 Prefab、Scene，或 UI Toolkit 的 UXML/USS、VisualTreeAsset 与 UIDocument。禁止将整张效果图作为场景或 UI 铺底来冒充结构化实现；每个图片节点必须引用批准资源，每个生成资源必须有消费节点，并核对父子层级、渲染顺序、Anchor、Pivot、遮罩、交互和全部状态。正式结构化拼装完成后，删除全部灰盒组件、占位 Mesh/Sprite/Material 和临时低保真 Prefab/Scene 对象，并清理序列化、场景、Prefab、地址和资源登记中的残留引用；保留已确认结构节点及稳定 ID，同时保留 `prefab-structure`、预览图、批准记录等审计证据。只有清理验证为 `PASS` 后，装配才可标记 `ASSEMBLY_VERIFIED`，场景才可继续进入 `DONE` 门禁。
8. 2D 场景按适配契约专门生成左右或上下边带背景；边带延续全局视觉但不复制、裁切或拉伸截图和效果图，不承载按钮、提示、可点击信息或玩法线索，并按独立资源登记和审查。
9. 为 Sprite、2D/UI 纹理、字体和 2D 动效记录尺寸、Pivot/Anchor、PPU、九宫格、颜色空间、压缩、MipMap、Read/Write、图集/地址、来源、授权和发布资格。
10. 从 Visual Bible 和已批准场景效果图提取 3D 造型语言、比例、材质语义、配色、磨损、表面细节与禁用项，形成版本化交接包；不得自行修改生产模型、UV、烘焙图、PBR 通道或 3D Prefab。
11. 对 `$unity-game-3d-modeling` 与 `$unity-game-3d-texturing` 的候选转台和 Unity 实机结果执行视觉一致性审查；技术验收仍由对应 3D 角色和独立 QA 负责。
12. 在目标分辨率、宽高比、安全区和交互状态矩阵下捕获 Unity 与 Windows 实机画面，与已批准效果图和结构版本比较；检查漏标元素、孤儿资源、缺图节点、层级/Anchor 漂移、黑边与状态缺失，修复 2D/UI 资源或把 3D 问题退回所属 3D Skill，重新捕获、复审，直到用户批准。

向两个 3D Skill 提供已批准的视觉基线与材质语义；向玩法提供当前有效的 2D/UI 资源 ID、GUID/地址、路径、规格、导入约定和限制；向 QA 提供逐项检查、清理验证、Unity 运行和预算证据；向发布提供权属与生成记录。复杂透明边缘缺少分层源或遮罩时必须阻塞，不伪造透明结果。上游需要回退时，从保留的结构、预览和批准证据重建所需灰盒，不得为了潜在回退在运行时保留低保真资产。
