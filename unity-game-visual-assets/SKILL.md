# Unity 视觉与资源接入

视觉流程按“全局视觉设计 → 三类独立审查 → 用户确认 → 每场景游戏效果图 → UI 效果图 → 资源重新生成 → 拆分前审查 → 拆分与逐项审查 → Unity 导入 → 实机对比”推进。全局视觉未批准时，场景效果图和正式资源只能处于阻塞状态。

## 输入与决策

读取 Visual Bible、当前场景 manifest、UI 信息架构、资源依赖、资源登记和性能预算。视觉方向、生成式资源、授权、预算、透明处理或发布资格需要取舍时，向总控提交决策包。

## 执行与交接

1. 先建立全局设计支柱、世界与 UI 语言、色彩、材质、光照、镜头、字体、图标、动效、可读性和禁用项；生成相互独立的方向图，完成视觉一致性、Unity 可实现性、UX/可读性审查，合并意见并请求用户批准 Visual Bible。
2. 每个场景分别生成游戏与 UI 效果图；版本化提示词、输入和输出，明确已批准 Visual Bible 是唯一风格权威，并迭代到三类审查和用户批准。
3. 把截图标记为内容、构图或信息层级参考；禁止复制截图的色彩、材质、光照、字体、图标、笔触和成品像素，也禁止直接裁切截图作为 Sprite、纹理或 UI 图。
4. 包含多个元素的效果图进入总控资源流水线：先依据已批准 Visual Bible 重新生成可生产源图，再完成拆分前审查、拆分、逐项检查、Unity 导入/场景验证和登记更新。效果图、截图和联系表不得直接冒充运行时资源。
5. 2D 场景按适配契约专门生成左右或上下边带背景；边带延续全局视觉但不复制、拉伸截图，不承载按钮、提示、可点击信息或玩法线索，并按独立资源登记和审查。
6. 为 Sprite、纹理、模型、字体、动画和 VFX 记录尺寸、Pivot/Anchor、PPU、九宫格、颜色空间、压缩、MipMap、Read/Write、图集/地址、来源、授权和发布资格。
7. 捕获 Windows 实机画面，与已批准效果图比较；修复资源或实现并重新捕获、复审，直到用户批准。

向玩法提供当前有效资源 ID、GUID/地址、路径、规格、导入约定和限制；向 QA 提供逐项检查、Unity 运行和预算证据；向发布提供权属与生成记录。复杂透明边缘缺少分层源或遮罩时必须阻塞，不伪造透明结果。
